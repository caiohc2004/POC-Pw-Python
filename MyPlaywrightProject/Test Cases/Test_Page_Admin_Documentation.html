Test_Page_Admin.py — Test Documentation

Playwright + pytest automated tests for the OrangeHRM "System Users" admin page, built with the Page Object pattern.

Overview

Test_Page_Admin.py contains a single test class, TestSystemUsers, with 4 async test methods. Each test logs in as an OrangeHRM administrator and exercises a different part of the Admin → User Management → System Users page, using the AdminLoginPage and SystemUsersPage page objects.

Target application under test: https://opensource-demo.orangehrmlive.com (OrangeHRM public demo).

1. test_navigate_to_system_users_page

test_navigate_to_system_users_page smoke

Verifies that an admin can log in and successfully reach the System Users page.

Steps:
  1. Call admin_login_page.login(username, password) — fills the Username and Password fields on the OrangeHRM login form and clicks Login.
  2. Call admin_login_page.assert_dashboard_visible() — asserts the Dashboard heading (h6:has-text('Dashboard')) is visible, confirming login succeeded.
  3. Create a SystemUsersPage instance reusing the same browser page and base_url.
  4. Call system_users_page.navigate() — goes to /web/index.php/admin/viewSystemUsers and waits for the page to load.
  5. Call system_users_page.assert_on_system_users_page() — asserts the URL contains /admin/viewSystemUsers and the User Management heading is visible.
Inputsadmin_credentials["username"] = "Admin"
admin_credentials["password"] = "admin123"
base_url
Expected OutputTest passes silently (no exception). Dashboard heading and System Users page heading/URL are visible after navigation.
Failure OutputAssertionError from Playwright's expect().to_be_visible() / to_have_url() if login fails or the page doesn't load correctly.

2. test_search_user_by_username

test_search_user_by_username smoke

Verifies that searching by an exact username filters the table and shows the matching user.

Steps:
  1. Log in with admin_login_page.login(...).
  2. Create a SystemUsersPage and call navigate() to open the System Users page.
  3. Call system_users_page.search_by_username("Admin"), which:
    • Expands the search filter panel if it's collapsed (ensure_filter_area_expanded()).
    • Fills the Username input (scoped to the filter form) with "Admin".
    • Clicks the Search button and waits for the results table to reload.
  4. Call system_users_page.assert_specific_user_visible("Admin") — asserts a table row whose Username column (2nd cell) exactly equals "Admin" is visible (avoids false matches from the "User Role" column, which can also contain the value "Admin").
InputsSearch term: "Admin" (hard-coded string)
Expected OutputExactly one row is found where the Username column equals "Admin"; assertion passes.
Failure OutputAssertionError: Locator expected to be visible if the username filter didn't apply or no matching row rendered within the timeout.

3. test_search_nonexistent_user

test_search_nonexistent_user regression

Verifies that searching for a username that doesn't exist correctly shows a "No Records Found" state instead of stale/incorrect results.

Steps:
  1. Log in with admin_login_page.login(...).
  2. Create a SystemUsersPage and call navigate().
  3. Call system_users_page.search_by_username("NonExistentUser12345") to search for a username that is not expected to exist in the demo data set.
  4. Call system_users_page.assert_no_records_found() — asserts the "No Records Found" message element is visible.
InputsSearch term: "NonExistentUser12345" (hard-coded string, deliberately not present in test data)
Expected OutputThe table renders zero rows and the "No Records Found" message is visible; assertion passes.
Failure OutputAssertionError if the "No Records Found" message never appears (e.g. stale results still shown, or the message selector no longer matches the UI).

Common Building Blocks

  • Page Object Pattern: Tests never touch raw selectors directly; they call methods on AdminLoginPage and SystemUsersPage, which encapsulate selectors and Playwright actions.
  • Assertions use Playwright's auto-retrying expect() API (via BasePage.assert_element_visible, etc.), so tests wait up to the configured timeout for the UI to reach the expected state before failing.
  • Markers: @pytest.mark.smoke tests cover core happy-path flows (login, navigation, search-and-find); @pytest.mark.regression tests cover secondary/edge behaviors (empty search results, UI element presence).
